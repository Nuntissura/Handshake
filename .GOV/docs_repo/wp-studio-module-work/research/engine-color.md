<topic id="engine-anatomy" status="current" summary="Engine internals a Rust rewrite must cover; facts marked from file/source reads vs UNVERIFIED">

- Profile = 128 B header (version, class, device space, PCS, intent hint) + tag table + tags. Read from installed files (this machine): Adobe RGB(1998), sRGB, ProPhoto = v2.1 matrix/TRC (`curv` 14 B = gamma; sRGB `curv` 1024-entry table; sRGB and Adobe RGB carry `bkpt`). SWOP/FOGRA39/GRACoL/PS5 CMYK = v2.1 class `prtr`, PCS Lab, A2B0/1/2 `mft2` (41-90 KB; PS5 395 KB), B2A0/1/2 `mft1` (145 KB; PS5 `mft2` 290 KB), `gamt` (mft1 37 KB). image P3, ACEScg = v4.2 matrix + `para`, `chad`. Adobe HDR/video (Rec2100 PQ/HLG W203, ARRI, HDR_UHD_ST2084) = v4.2 class `mntr` RGB->XYZ with A2B0/1 `mAB ` + B2A0/1 `mBA ` (PQ 30 KB; HLG 973 KB), `lumi`, `chad`; film previews (Kodak 2383 Theater Preview) = class `scnr`, PCS Lab, mAB/mBA. No `mpet` in any sampled Adobe profile.
- Curves: `curv` (count 0 = identity, 1 = gamma u8Fixed8, n = table), `para` types 0-4 (Prism admits 1,3,4,5,7 params). LUT forms: lut8 `mft1` / lut16 `mft2` (fixed: matrix only if XYZ in, input curves, CLUT, output curves; v2 Lab uses legacy 16-bit encoding) and v4 `mAB `/`mBA ` (A2B: A curves, CLUT, M curves, 3x3+offset, B curves; grids may differ per axis). `mpet` (D2B/B2D, v4.3+ float multi-process elements) = rarest; low priority since Adobe's own HDR profiles avoid it (file read).
- PCS: XYZ D50 (0.9642, 1, 0.8249), u1Fixed15 range 0..1.99997; Lab v2/v4 encodings differ. Unbounded float outside PCS range is clipped by classic CMMs (see differences). Profile colorants are already D50-adapted; `chad` is informational for matrix profiles; adaptation is needed when building a profile from primaries/CICP (Bradford default in moxcms `chad.rs`) and for absolute colorimetric.
- Intents are realised by TAG SELECTION, not CMM maths: perceptual/saturation = A2B0/B2A0 and A2B2/B2A2, colorimetric = A2B1/B2A1; matrix/TRC profiles are colorimetric only (a single transform cannot hold gamut mapping); all gamut mapping lives in the profile's B2A tables (Argyll doc). Relative = white-scaled colorimetric; absolute = relative with media white restored (lcms `AdaptationState` 0..1 adds observer-adaptation control). Missing intent table -> fallback is engine-specific: moxcms has NO fallback (`get_device_to_pcs` returns None -> `UnsupportedLutRenderingIntent`, e.g. a profile with only A2B0 fails Relative); lcms2 and ACE UNVERIFIED (test H9).
- v4 perceptual intent is defined against a reference medium (black ~ XYZ 0.00336, 0.00347, 0.00287; both lcms2 and moxcms hard-code this constant) so v4 perceptual implies a fixed black; BPC-on-by-default for v4 perceptual/saturation is what lcms2 does (`cmscnvrt.c`).
- BPC = PCS-space affine scaling between detected black points (full algorithm in topic `bpc-algorithm`). CMYK: dest black from Lab(0,0,0) through perceptual B2A (ink-limit aware); lcms discounts embedded ink limits via round trip.
- CMYK specifics: ink limit/TAC is a property of the separation baked into B2A (ECI says ISO Coated v2 330% vs 300% on same data - prep file); lcms `cmsDetectTAC` + black-preserving intents 10-13 (K-only maps pure K via a tone curve; K-plane re-solves CMY at fixed K to hold Lab and respect TAC); PS "Preserve CMYK numbers" = bypass UNVERIFIED. 4D CLUT: tetrahedral over 3D sub-cubes + linear over 4th axis.
- Interpolation + grids: lcms2 default precalc grid = 33 (3ch) / 17 (4ch) / 7 (>4), HIGHRES 49 / 23 (`cmspcs.c`), tetrahedral for 3D; moxcms default `Linear` (tri/quadlinear), tetrahedral/pyramid/prism behind feature `options`; moxcms bakes CMYK->RGB to a 17^4 grid on the non-katana path (`lut_transforms.rs` GRID_SIZE=17). Precision: float vs Q0.15/Q2.13 fixed (moxcms default `prefer_fixed_point:true`); Photoshop 16-bit = 0..32768 internally ("15+1", Adobe community, Chris Cox).
- Gamut check/soft proof: lcms2 builds a 1-channel table by Lab->dest->Lab round trips (relative intent, dE threshold 5, 1.0 for matrix profiles, 0xFFFE for hard clip) and does NOT read `gamt`; ICC printer profiles still carry `gamt` mft1 (seen in all CMYK profiles here). Soft proof = src -> proof device (B2A then A2B, proof intent, optional paper/black simulation) -> display. Photoshop's gamut-warning source UNVERIFIED (test H7).
- Device link (class `link`): single LUT bypassing PCS; intent/BPC inert (spec STU-COL-134). Named colour (`ncl2`): table lookup bypass. Both are absent from moxcms.
- OCIO/ACES: config-driven op graph (roles, colorspaces, looks, display/view); ACES 2.0 officially supported from OCIO 2.4.2, built-in ACES 2 configs listed for 2.5 (UNVERIFIED primary); GPU path via generated shaders (Metal/Vulkan mentioned in release notes). HDR in ICC: PQ/HLG baked as LUTs at fixed reference white (names `W203`); v4.4 adds `cicp` tag; ICC HDR WG says v2/v4 PCS is limiting, pointing to v5/iccMAX.

<topic id="documented-engine-differences" status="current" summary="Public evidence on ACE vs lcms vs others; anecdotal items labelled">

- Pedigree: BPC first shipped in Photoshop 5.0 (1998); Adobe published its algorithm 2005/2006; ICC/ISO 18619:2015 standardised it, explicitly correcting items the Adobe paper left open. HP (Marti Maria) validated an lcms-based implementation against Adobe on 238 profiles x 3 intents x 2 inputs, "highly consistent" (no numbers published in slides). lcms2 `cmsDetectDestinationBlackPoint` is the "Adobe-style" curve-fit routine.
- Documented quirk list: (1) PCS clipping - ACE, ColorSync, Windows ICM clip at PCS; Photoshop CS4 Lab(0,-120,0)->sRGB(0,0,0) but Lab(0,0,-120)->sRGB(0,27,182) (Maria, CIC18); lcms2 offers unbounded float. (2) 16-bit is 0..32768 internally. (3) rendering-intent integers differ across Adobe apps (prep spec STU-COL-135).
- ANECDOTE / UNVERIFIED: PS applies BPC under Perceptual regardless of the checkbox (Capture One KB); OpenICC 2007 thread: PS CS2 perceptual CMYK differed with/without BPC while lcms `icctrans` did not (v2 profiles; conflicting with a later report that CS2 shows no difference); Kasson blog (403 on fetch, search snippet only): ACE accurate for RGB->RGB/Lab, Microsoft ICM worse, possible Lab-error bias. ACE source behaviour for absolute colorimetric, missing intent tables, gamut tag, grid size and SIMD is undocumented -> measure (topic black-box-plan), do not guess.
- lcms2 vs moxcms (source + GitHub issues): lcms2 forces BPC off for absolute and on for v4 perceptual/saturation; moxcms hard-codes BPC only for RGB v4 LUT profiles, perceptual/saturation, constant black, CMYK = none (issue #162: "lcms2 applying BPC which moxcms did not", fixed hard-coded in PR #181, proper handling "next major version"). moxcms fixed-point trilinear vs lcms2 up to 14/255 on a wide-gamut profile, tetrahedral <=3/255 (issue #162); CMYK yellow-axis error up to 8/255 vs lcms2/skcms (issue #144, fixed). `allow_use_cicp_transfer` default true breaks PQ/HLG ICC (issue #155, closed "not a bug", apps must disable).
- Other engines: Argyll = no ICC v4, gamut mapping uses CIECAM02, precomputed mappings only valid with their source profile; skcms = A2B only (no B2A); qcms = browser display engine; lcms2 = full ICC 4.4 incl. CMYK<=15 inks, devicelink, named colour, float plugin, gamut check, CIECAM02.

<topic id="bpc-algorithm" status="current" summary="Published BPC algorithm steps for a builder (ISO 18619 / ICC final-approved version)">

Source: ICC "final approved ICC version of ISO 18619" (committee draft 2013-05, read in full) https://www.color.org/BlackPointCompensation.pdf (redirects to https://archive.color.org/files/BlackPointCompensation.pdf); ISO 18619:2015 (paywalled, UNVERIFIED identical); ICC White Paper 40 (2010); Adobe "Adobe Systems' Implementation of Black Point Compensation" (2006; URL NOT retrieved); cross-check lcms2 `cmssamp.c` (`cmsDetectDestinationBlackPoint`) and `cmscnvrt.c` (https://github.com/mm2/Little-CMS). Implement from the ICC text; do not copy GPL/others' code.
1. Inputs: source profile, destination profile, one intent in {Relative, Perceptual, Saturation} (same both sides; Absolute excluded; lcms forces BPC off for absolute). Classes Input/Display/Output/ColorSpace; spaces Gray/RGB/CMYK/Lab; destination needs a PCS->device transform. Let T(x,P1,P2,intent) = profile-to-profile transform, `LabIdentity` = virtual Lab<->PCS-Lab identity profile.
2. D(profile,intent) = darkest device vertex = the one with lowest L* via T->Lab among: Gray {0,1}; RGB {000,111}; CMYK {0000,1111,0001,1110}.
3. SourceBlackPoint: LocalBlack = T(Lab(0,0,0)->src device, Perceptual) if src is an output-capable CMYK; (0,0,0) if src is Lab; else D(src,intent). Li = L* of T(LocalBlack, src->Lab, intent). SourceBP = (min(Li,50),0,0).
4. DestinationBlackPoint, not LUT-based (gray/RGB matrix): LocalBlack = D(dst,intent); Li as above; DestBP = (min(Li,50),0,0).
5. DestinationBlackPoint, LUT-based: InitialLab = (0,0,0) unless intent is Relative; if Relative: LocalBlack = T(Lab 0,0,0->dst, Perceptual) for CMYK, (0,0,0) for Lab, D(dst,intent) for Gray/RGB; InitialLab = T(LocalBlack, dst->Lab, Relative); CMYK: a=b=0; L*=min(L*,50). inRamp = 256 Lab points from (0,ka,kb) to (100,0,0) with ka,kb = InitialLab a,b clamped to +-50. outRamp[i] = L* of BT(inRampLab[i]) where BT = Lab->dst device (given intent) then back to Lab (Relative). Make outRamp monotonic: for i=last-1..first outRamp[i]=min(outRamp[i],outRamp[i+1]). If outRamp[first] >= outRamp[last]: DestBP=(0,0,0). If intent Relative and "mid range straight" (every i with inRamp[i] > MinL+0.2(MaxL-MinL) has |inRamp[i]-outRamp[i]| <= 4 - comparison operator garbled in the text extraction, lcms2 uses this reading): DestBP=InitialLab. Else curve fit: yRamp[i]=(outRamp[i]-MinL)/(MaxL-MinL); shadow points = indices with 0.1<=yRamp<0.5 (Relative) or 0.03<=yRamp<0.25 (others); fewer than 3 points (lcms2 needs 4): DestBP=0; fit least-squares y=a x^2+b x+c over (inRamp,yRamp); if |a|<1e-10 z=clamp(-c/b,0,50) else d=b^2-4ac, z=0 if d<=0 else clamp((-b+sqrt d)/(2a),0,50); DestBP=(z,0,0).
6. Map: only L* used. Y(L) = ((L+16)/116)^3 for L>8; Y(L) = L*((8+16)/116)^3/8 for 0<=L<=8 (second branch inferred from continuity at L=8; operator garbled in extraction). scale = (1-Y_dst)/(1-Y_src); offset = (1-scale)*W, W = PCS D50 white (0.9642, 1.0000, 0.8249).
7. Apply between source->PCS and PCS->destination, in PCS XYZ (convert Lab PCS to XYZ first): XYZ_dst = scale*XYZ_src + offset. Result depends only on profile pair + intent, so it can be folded into the cached materialised transform (cache key already carries BPC, STU-COL-142).
8. Studio notes: BPC stays an independent boolean (STU-COL-136); matrix/TRC dest with zero black -> scale 1; moxcms's built-in BPC (constant black, v4 RGB LUT only, perceptual/saturation, no switch) must be disabled or bypassed or it double-applies.

</topic>

<topic id="spec-oracle-reading" status="current" summary="Does STU-COL-140 forbid LittleCMS as an offline oracle? Reading + compliant approach">

Quote (14-studio-creative-suite.md line 10144-10147, STU-COL-140): "Studio MUST NOT depend on a platform colour management module (Windows ICM/WCS, macOS ColorSync), on a system-installed LittleCMS, or on a subscription colour service, at runtime, on any platform, in any build profile, including tests." Related: acceptance check `col.no_platform_cmm` = "No platform colour management module or system colour library in the graph"; STU-COL-141 = own ICC or vendor a PURE-RUST CMM; STU-COL-325 = "Every expected value ... MUST come from an independent source: a published reference table, an independently implemented reference computation, or a physical measurement. Where an expected value is produced by a second implementation ... the corpus record MUST name that implementation and its version."
Reading (lead-level, not legal/spec authority): the ban is on DEPENDING (product/runtime/build/test graph). A generator that lives outside the workspace graph and whose only effect on the repo is committed numeric fixtures is not a dependency; STU-COL-325 requires, and 143's "an engine cannot be its own authority" motivates, exactly such second-implementation values with name+version. Risks: (a) a vendored-static lcms2-sys as a workspace dev-dependency is not literally "system-installed" but sits in the graph, is C (141), and fails `col.no_platform_cmm` in spirit - avoid; (b) fixtures must hold numbers + profile SHA-256 + tool name/version/flags, not tool code; (c) committing third-party profile bytes needs a licence check (Adobe/HP/Windows profile redistribution terms UNVERIFIED) - prefer SHA-256 references or ICC-published permissive profiles; (d) GLOBAL-CLOSURE-042: the Prism builder lane must not author the oracle producer. If the lead wants in-workspace lcms, get an Operator spec decision first.
Compliant oracle ladder (record tier per fixture): T0 analytic from published primaries/transfer functions in f64 (no CMM; covers current Prism matrix/TRC scope; STU-COL-324 synthetic set). T1 offline lcms2 2.19.1 (MIT; v2+v4, all intents, BPC; separate Cargo project under `Handshake_Artifacts/WP-KERNEL-STUDIO/oracle-color/`, D: build env, not a workspace member) -> fixtures.
