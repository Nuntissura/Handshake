# File-Format Strategy Research (Cloth + BodyKit)

## MD formats findings

- **Native formats are fully proprietary and undocumented.** `.zprj` (project), `.zpac` (garment: 3D garment + 2D patterns + fabrics + subsidiary materials), `.zfab` (fabric), `.avt` (avatar), `.pose`, `.zsp` are described in MD's manual only at the usage level (open/save semantics); no internal structure is published anywhere on support.marvelousdesigner.com or developer.marvelousdesigner.com. The MD "API" is an in-app automation API that *loads* zprj/zpac inside MD — it is not a format spec.
- **No open-source reader/writer exists.** Targeted searches (GitHub topics, "zprj/zpac parser", reverse-engineering queries, Blender Artists) found zero parsers, zero structure write-ups. The one community thread on ZPAC ends with "convert to OBJ or FBX." This is a strong negative signal: after ~12 years of MD's market presence, nobody has shipped even a partial reader.
- **MD's sanctioned interchange surface is broad and getting broader:** OBJ, FBX, Alembic, PC2/MDD/Maya cache, DXF-AAMA (2D patterns), USD ("USD Export Simulation Data" targeting UE 5.4+ Chaos Cloth), and glTF/GLB export (listed as of MD 2026.0 — UNVERIFIED exact version). MD's own strategy is: proprietary authoring file + standard export lanes. Version-compatibility landmines exist even in MD's own USD lane (MD 2025.0 ↔ UE 5.4 only; MD 2025.2 ↔ UE 5.6+; UE 5.5 explicitly incompatible).
- **Legal posture (engineering-level, not legal advice):** clean-room reverse engineering for interoperability is the established lawful pattern (Sega v. Accolade fair-use holding in the US; EU Software Directive 91/250 Art. 6 permits decompilation "indispensable to achieve interoperability" and Art. 9(1) voids contract terms forbidding it). So a zpac reader is legally *defensible* — but economically irrational: no spec, no prior art to build on, per-release format churn, and every MD project can already be exported to open formats by its owner from inside MD.

## DSON/DUF findings

- **The DSON spec is real, public, and JSON-based.** docs.daz3d.com hosts the "DSON File Format Specification," version **0.6.1.0** (first public with Daz Studio 4.5); page licensed CC-BY 3.0. Design goals stated: lightweight, human-readable, "simple to parse due to its JSON syntax," asset-referencing scheme rather than inline storage, "designed for legal sharing." Binary form is just zlib/gzip-compressed text (`.duf` saved with "Compress Files" is gzip; uncompressed is editable in a text editor).
- **The spec is frozen in ~2012.** It covers 0.6.1.0 / DS 4.5-era semantics. Later features are outside it: notably **HD morphs (`.dhdm`) are an undocumented proprietary binary** ("encoded in an undocumented binary format and can not be read by the DAZ Importer"), and HD-morph authoring tooling is restricted to Daz PAs. A third party (Xin) reverse-engineered dhdm anyway (source on GitLab) — proving both the gap and its work-around cost. Daz Studio Premier still saves `.duf` scenes (UNVERIFIED — no evidence of a Premier-specific format change found).
- **Third-party read is proven feasible at production quality.** Diffeomorphic `import_daz` (Blender add-on, community-maintained on GitHub, current with Blender 5.x) imports native `.duf`/`.dsf` with full morph → shape-key support for Genesis 3/8/9; zDsonImport does the same for Maya. Community consensus is that Diffeomorphic beats Daz's own official bridge.
- **The critical dependency: DUF is a reference graph, not a payload.** A `.duf` scene references geometry/morph `.dsf` files, OBJ/Poser files, and textures by URI into the user's installed Daz content library. Diffeomorphic requires configured Daz root paths and an "intact DAZ database"; morphs drive other morphs, so partial libraries break. Without the (paid, non-redistributable) Genesis content, a DUF file reconstructs nothing. Any Handshake DUF importer therefore only works *against the user's own Daz install* — it can never be a standalone content lane, and Handshake can never ship Genesis-derived base meshes.

## Pattern interchange findings

- **DXF-AAMA / ASTM D6673 is the de-facto 2D pattern interchange** (pattern pieces, grading, 23 predefined layers on DXF R13, grade rules in an ASCII `.RUL` sidecar). The ASTM standard was **withdrawn in 2019 with no replacement**, yet CLO/MD/Gerber/Lectra/Optitex all still speak it. Known field quirks: seam-allowance corners distorted on round-trip, notches dropped, CLO exports nested grading with **no RUL file** (grade table lost), and "the DXF-AAMA format is different for every system." CLO's own guidance: never treat DXF-AAMA as a fidelity-preserving round-trip; keep origination in the native tool. Implementable on top of a generic DXF library (ezdxf discussion demonstrates the layer/block conventions).
- **GarmentCode is the best open, modern garment representation.** MIT-licensed parametric sewing-pattern DSL (ETH Zurich / Korosteleva) with a hierarchical **JSON pattern spec (panels, edges, stitching rules)**, PyGarment implementation, active through 2025 (v2.0.0, 1500+ commits). A research/industry ecosystem is converging on it: ChatGarment (CVPR'25), DressCode, and Design2GarmentCode — the latter co-published by **Style3D**, i.e., a commercial MD competitor is already treating GarmentCode as an interchange target.
- **Competitive context confirms the industry pattern:** Browzwear's `.bw` (single-file, proprietary, superseded VSP/VSGX) and Style3D's project format are closed; every vendor pairs a proprietary native with DXF-AAMA + mesh-format export. No ISO standard for 3D garment/sim interchange exists (UNVERIFIED as absolute negative). USD has no ratified cloth/pattern schema; MD's "USD Export Simulation Data" → UE Chaos Cloth is a vendor-to-vendor lane, not a standard.

## Recommendation

**Answer to the operator: No — do not use MD's or Daz's file types as the native format for either clone.** Use them (selectively) as compatibility lanes only, and only where a spec actually exists (DSON — yes; zprj/zpac — no spec, so no).

### Native format decision
- **Authority: Handshake-native typed model (PostgreSQL/EventLedger + typed GarmentSpec/BodySpec), per existing project mandate.** Every vendor in this market (MD, CLO, Browzwear, Style3D, Daz) authors in a private native model and treats files as export products; none authors in a competitor's format. File formats become import/export lanes only.
- **On-disk project serialization (when needed): Handshake-native versioned JSON** — pattern layer shaped GarmentCode-like (panels/edges/stitches, MIT prior art to borrow from), stealing DSON's two proven ideas: URI asset referencing instead of inline blobs, and human-readable text with an optional gzip twin.
- **Why not .zprj/.zpac:** undocumented proprietary binary, zero open tooling after a decade, per-version churn, clean-room cost with no payoff — every MD user can already export USD/Alembic/OBJ/DXF-AAMA from MD itself.
- **Why not .duf as native:** spec frozen at 0.6.1.0 (DS 4.5 era, ~2012); HD morphs live outside it in undocumented `.dhdm`; DUF is a URI-reference graph into a paid content library Handshake cannot ship; it encodes Daz Studio scene semantics, not Handshake authority semantics; and it would conflict with the EventLedger authority model. Compatibility ≠ adoption.

### Import matrix
| Lane | Verdict | Rationale |
|---|---|---|
| DXF-AAMA (patterns) | **P1** | De-facto industry 2D pattern interchange; gets real patterns from MD/CLO/Gerber into Cloth; expect per-vendor quirk handling (seam corners, RUL loss) |
| GarmentCode JSON | **P1** | MIT, documented, parametric — closest existing thing to Cloth's authoring model; research+Style3D ecosystem converging on it |
| OBJ (+FBX via ufbx, glTF) | **P1** | Universal mesh/avatar ingestion; ufbx is MIT and field-proven (Godot, Blender) |
| DUF/DSF (DSON read) | **P2** | Published JSON spec + Diffeomorphic proves production feasibility; kills BodyKit migration friction for Daz users. Constraints: works only against user's installed Daz library; no `.dhdm` HD morphs; never redistribute Genesis-derived data |
| USD / Alembic (from MD) | **P2** | Consume MD users' garments+sims via MD's own sanctioned export lanes instead of cracking zpac |
| .zprj/.zpac | **Reject** | No spec, no prior art, version churn; clean-room legal path exists but ROI is negative |
| SMPL-X params | **P3 (optional)** | Useful for mocap/research pipelines; user supplies MPI/Meshcapade-licensed model files; keep out of core |

### Export matrix (Blender + UE5 are the acceptance targets)
| Lane | Verdict | Rationale |
|---|---|---|
| glTF 2.0 | **Primary (bodies/garments, skeletal+morphs)** | Only open format that is first-class in Blender and native-ish in UE Interchange; pure-Rust writable today; validate against UE's known morph-import bugs and morph-count scaling |
| Alembic | **Primary (cloth sim caches)** | The industry lane for baked cloth into UE Geometry Cache and Blender Mesh Sequence Cache; budget for C++ FFI writer and mitigate known pains (file size, frame-offset sync) |
| OpenUSD | **Secondary, strategic** | The only lane covering whole scenes + UsdSkel + the UE Chaos Cloth sim-data path MD itself uses; native Rust write support exists (`mxpv/openusd`, young); UE support still "experimental" but Epic momentum is clearly here |
| FBX | **Deferred / proxy** | Unavoidable for legacy UE character pipelines; official SDK is a non-starter for Rust redistribution. Handle via: (1) adopt `ufbx_write` when it matures (Blender/Godot are both waiting on it), (2) until then document a Blender round-trip (glTF/USD → Blender → FBX) as the sanctioned path |
| OBJ | **Ship day 1** | Static garments/bodies; trivial |
| MDD/PC2 | **Cheap add-on** | Day-effort writers; gives Blender-only users a lightweight cache lane MD users already know |

**Uncertainties:** `ufbx_write` maturity as of mid-2026 (UNVERIFIED); UE native glTF morph-import bug status in 5.6+ (bug confirmed for 5.4.x, current status UNVERIFIED); MD glTF export version 2026.0 (UNVERIFIED); Daz Studio Premier format unchanged (UNVERIFIED); absence of ISO garment-sim standard (negative claim, UNVERIFIED).
