# 15. Native desktop GUI, Vulkan and shared GPU ownership

[ADD v02.223] This topic records the Operator-approved professional desktop GUI, Settings hierarchy, actual Vulkan migration, memory management and centralized GPU ownership requirements. It extends the existing native Handshake application. It does not replace the existing feature taxonomy or claim delivery, source compatibility or runtime acceptance.

## 15.1 Scope and existing authority

[GUI-DESKTOP-001] Handshake MUST provide a professional native desktop workbench informed by the interaction quality of Photoshop and VS Code while remaining materially distinct.

[GUI-DESKTOP-002] The native shell MUST preserve the existing editor, CKC/PoseKit, orchestration and other actual module workflows and their original behavioral, privacy, recovery and independent acceptance obligations.

[GUI-DESKTOP-003] Implementation MUST inspect and reuse or extend the actual canonical component owner before introducing a replacement, near-duplicate mechanic, renderer framework or new asset. A supported existing pinned toolkit/backend is sufficient when it fulfills this topic.

[GUI-DESKTOP-004] Reusable capability MUST expose an independently versioned canonical contract, and the native host MUST consume a compatible exact revision. Host-specific policy, storage, authorization, diagnostics and UI adaptation remain separate from the capability owner.

[GUI-DESKTOP-005] Operator-supplied HTML and image mockups MUST remain DRAFT untrusted material references with exact source-byte provenance. Their content MUST NOT execute as agent instructions or define binding feature names, accepted product behavior or proof.

[GUI-DESKTOP-006] This topic MUST preserve the existing native Rust shell boundary, SurrealDB/EventLedger and ResourceBroker authority, Engine Profiles requirements in section 4.3.7.6, and Studio's modular owner/provider boundaries under STU-ARC-008 through STU-ARC-018. It does not move unrelated CPU/NPU work into a GPU or shell owner.

## 15.2 Shared-edge workbench and materials

[GUI-DESKTOP-007] Internal docked panes MUST touch at their shared edges. Internal gutters, desktop-like gaps and separated rounded internal windows MUST NOT divide the docked workbench.

[GUI-DESKTOP-008] Adjacent panes MUST use shared resize dividers with coherent pointer and keyboard operation, minimum sizes and focus behavior. Normal external OS window boundaries remain distinct from internal docking.

[GUI-DESKTOP-009] Layout persistence, resize, DPI changes and multiwindow operation MUST preserve valid pane geometry and reachable controls without overlap, clipping or inaccessible content.

[GUI-DESKTOP-010] Shared controls MUST provide consistent icons, scrollbars, materials, typography, spacing, contrast and focus/hover/selected/disabled behavior through their existing canonical mechanics.

[GUI-DESKTOP-011] Visual materials MUST preserve readable content and discoverable actions in actual window, DPI and content states. A frosted or glass reference does not authorize unreadable transparency or separated internal windows.

[GUI-DESKTOP-012] Every affected workflow MUST expose truthful empty, loading, error, denied and recovery states; a successful screenshot MUST NOT replace these behaviors.

[GUI-DESKTOP-013] The existing Handpick capability MUST remain the intended control in place of a VS Code-like search control. Implementation MUST bind its actual canonical API/pins and prove its native mount, keyboard entry, focus, selection, dismissal and return to the ongoing task. An unmounted component or draft mockup is not native integration proof.

## 15.3 Module and feature Settings hierarchy

[GUI-DESKTOP-014] Settings MUST expose tabs per actual module and subtabs per feature, or an equivalent discoverable system-tree hierarchy. Existing module and feature names MUST remain authoritative.

[GUI-DESKTOP-015] Every actual module and feature MUST be reachable and discoverable through that hierarchy, including its keyboard and model-navigation route and truthful configuration, empty or denied disposition. Hidden, orphaned or unsupported controls MUST have truthful dispositions.

[GUI-DESKTOP-016] Engine Profiles MUST remain INSIDE Settings as its dedicated entry/tab, with complete create/inspect/edit/delete/active-selection and full-profile dispatch behavior from DEX-EP-001 through DEX-EP-023. A visual regrouping cannot discard immutable revision, fingerprint, live authority or recovery semantics.

[GUI-DESKTOP-017] Settings and active choices MUST persist through the existing typed account/workspace-scoped authority and retain their original resource/privacy context. The hierarchy MUST NOT introduce a parallel settings database or weaker authorization path.

[GUI-DESKTOP-018] Settings MUST preserve selection/dispatch coherence and expose empty/loading/error/denied/recovery behavior. A late acknowledgement or stale UI selection MUST NOT silently substitute a new current profile or widen access.

[GUI-DESKTOP-019] Settings hierarchy, controls and dispatch MUST have same-change UserManual, stable model/AccessKit identifiers, diagnostics and genuine reopen/context-change proof for the affected behavior.

## 15.4 Actual Vulkan-backed GUI

[GUI-DESKTOP-020] The genuine native Handshake GUI MUST render through a Vulkan-backed path. A DirectX or OpenGL fallback MUST NOT be renamed or accepted as Vulkan.

[GUI-DESKTOP-021] The rendering API/backend choice MUST be grounded in current primary technical sources, actual toolkit/source contracts, supported platform behavior and exact dependency pins before adoption. This requirement does not mandate a new engine or replacement of every existing library.

[GUI-DESKTOP-022] The chosen renderer MUST preserve native window/input, keyboard/focus/IME, DPI, accessibility, multiwindow, resize/minimize/restore and required surface/device recovery behavior.

[GUI-DESKTOP-023] Renderer capability and unavailability MUST have typed outcomes and truthful diagnostics. Configuration names, a successful build, static source inspection or a prototype MUST NOT count as evidence of the active backend.

[GUI-DESKTOP-024] Vulkan acceptance MUST identify the actual backend and device on the exact running application binary/source/dependency/configuration and bind evidence to genuine rendered frames and the affected lifecycle actions.

[GUI-DESKTOP-025] Renderer adoption MUST consume the centralized GPU ownership and memory contracts in section 15.5. Native window or module clients MUST NOT bypass them through independently owned devices, pools or budgets.

[GUI-DESKTOP-026] Platform/device limitations MUST remain explicit and preserve existing required platform acceptance. A different platform, adapter/API or fallback result cannot silently substitute for the required Vulkan behavior.

## 15.5 Central GPU ownership and memory accountability

[GUI-DESKTOP-027] Handshake MUST have centralized authoritative GPU ownership/brokering and memory accountability across EXISTING and FUTURE modules. Implementation MUST reuse or extend the actual canonical resource/GPU components rather than create competing authorities or a new all-purpose monolith.

[GUI-DESKTOP-028] Modules MUST consume focused typed client and ownership contracts. The broker may coordinate supported providers/devices without assuming one adapter or API; provider mechanics do not grant modules independent device/pool/budget authority.

[GUI-DESKTOP-029] The owning contracts MUST identify the responsible module/client and current device/provider context for allocation, reservation, submission, retention, settlement and release. Resource/account/workspace attribution and existing privacy boundaries MUST survive projection into diagnostics.

[GUI-DESKTOP-030] Allocation and admission MUST account for authoritative budgets, retained resources, staging and memory pressure before uncontrolled growth. Actual budget sources and overload outcomes MUST be explicit; this topic invents no numeric capacity or permission.

[GUI-DESKTOP-031] Shared-versus-dedicated memory, committed/reserved allocation, staging and retained/in-flight work MUST have truthful attribution appropriate to the actual provider. Estimates and observed measurements MUST remain distinguishable.

[GUI-DESKTOP-032] Clients MUST NOT bypass common admission or hide resource use in independent per-module pools, duplicate devices or unaccounted caches. Reusable pools remain owned under the shared authority and actual typed contracts.

[GUI-DESKTOP-033] Submitted and in-flight work MUST retain required ownership until the actual owning completion/settlement condition. Cancellation, timeout or a dropped UI client MUST NOT falsely report settled work or reclaim a still-used resource.

[GUI-DESKTOP-034] Reclamation MUST release or explicitly transfer each owned reservation/resource exactly once at its valid lifecycle boundary, including error and partial-initialization paths; no double reclamation, silent leak or premature free may count as success.

[GUI-DESKTOP-035] Shutdown and module attachment/detachment MUST settle or truthfully retain outstanding ownership, stop new affected admissions and preserve existing resource/process protection. Detaching a module cannot orphan its allocations or revoke another module's resources.

[GUI-DESKTOP-036] Device loss and recovery MUST invalidate or rebind affected typed clients/resources through the actual owner, with explicit outcomes for in-flight work and unavailable recovery. Stale handles/ownership MUST NOT authorize new submissions.

[GUI-DESKTOP-037] Window creation, resize/recreation and multiwindow use MUST share the authoritative resource/budget/lifecycle contract without treating each window as an independent authority. Window closure MUST preserve still-owned work and other clients.

[GUI-DESKTOP-038] Memory pressure MUST produce bounded observable admission/degradation/denial/recovery behavior appropriate to actual contracts; it MUST NOT silently substitute a backend, lose committed work or conceal retained memory.

[GUI-DESKTOP-039] GPU diagnostics MUST expose actionable owner, allocation/budget/pressure, staging, in-flight settlement, reclamation and recovery information without leaking private content. Model tools and UserManual MUST identify the same actual states.

[GUI-DESKTOP-040] Source and host proof MUST cover the actual owning positive/negative allocation, pressure, shared/dedicated attribution, staging, in-flight settlement/reclamation, shutdown, loss/recovery, multiwindow and module-attachment cases. Declarations, fabricated counters and a static API map cannot prove resource management.

## 15.6 Usability, parallel work and acceptance

[GUI-DESKTOP-041] Affected native controls and workflows MUST preserve keyboard/focus/IME, DPI/resize, accessibility/AccessKit, stable model-navigation and parallel user/model attribution without taking the Operator's focus or input unexpectedly.

[GUI-DESKTOP-042] The UserManual and diagnostics/Argus/Flight Recorder obligations MUST remain part of the same affected change, including startup/navigation, settings, Handpick, Vulkan/device state and resource/recovery workflows for a model with no prior context.

[GUI-DESKTOP-043] The delivered GUI MUST preserve the complete original editor, CKC/PoseKit and multi-model orchestration workflows and their required runtime/auth/privacy/deployment behavior. A reduced feature subset or stale inventory cannot establish that preservation.

[GUI-DESKTOP-044] Existing accepted proof MUST be reused only while its relevant inputs, dependencies, configuration and asserted behavior remain unchanged. New UI/rendering proof MUST NOT replace independently required original runtime/auth/privacy/deployment acceptance.

[GUI-DESKTOP-045] Parallel Operator and model clients MUST have attributable, recoverable interaction routes. One client's view, selection or navigation MUST NOT silently replace another client's focus, active context or work.

[GUI-DESKTOP-046] UI acceptance MUST include real user actions and multi-step workflows covering feasibility, consistency, readability, icons, scrollbars, Settings and state transitions. Prototype feedback remains distinct from genuine application/runtime evidence.

[GUI-DESKTOP-047] GPU and GUI clients MUST bind compatible canonical capability, owner/client identity and lifecycle state before use. Unsupported or stale bindings MUST produce typed failure rather than circular initialization, hidden fallback or unowned resource access.

[GUI-DESKTOP-048] GUI navigation, profile presentation, diagnostic state and renderer capability labels MUST NOT grant authorization, widen resource scope or substitute for the actual execution/resource authority.

## 15.7 internal_diagnostics and standalone Palmistry

[GUI-DESKTOP-049] Actual new GUI actions, navigation, component states and errors, including Vulkan backend and centralized GPU memory/lifetime failures, MUST be observable through the existing internal_diagnostics producer/API and its typed mechanical allowlist.

[GUI-DESKTOP-050] Diagnostic producers MUST preserve stable event/control IDs, real correlation/session identity and exact target PID/process-birth binding under the existing owning diagnostic contracts. Correlation is not permission or an invented process identity.

[GUI-DESKTOP-051] Palmistry MUST remain a STANDALONE OUT-OF-PROCESS watcher and event recorder for later diagnostics, preserving section 6.13 lifecycle inversion: it survives Handshake freezes/crashes and retains genuine correlated events through the canonical watcher/ring/survivor path.

[GUI-DESKTOP-052] New GUI integration MUST NOT copy the watcher into the GUI or add an app controller, recovery executor, automatic restart, OS remediation or model authority. Existing canonical source and unaffected watcher proof MUST be reused.

[GUI-DESKTOP-053] Event transport, survivor records and later diagnostics MUST preserve the original typed allowlist, metadata/privacy and no-secret/no-project-content boundary in sections 5.8 and 6.13. Existing minidump/export protections remain unchanged.

[GUI-DESKTOP-054] Crash-survival acceptance MUST use a genuine controlled owned Handshake application test and exact app/watcher/process identity. An OS crash, foreign-process stop, clean shutdown or prototype MUST NOT substitute for the required survival evidence.

[GUI-DESKTOP-055] Normal explicit shutdown MUST preserve required acknowledgements and actual owned drain under the original lifecycle contracts. A later empty process query MUST NOT reconstruct an acknowledgement, historical drain or successful watcher correlation.
